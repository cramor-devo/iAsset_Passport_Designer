# 0.5.0-06 Design profile refinements from the refined Wave 2 workbook (PO item 6)

Status: draft · Size: M–L · Builder: **Sonnet** (profile data), **Opus** (importer heuristics, step 4) · Depends on: –

## Source
The PO attached `Paspoortinrichting Wave 2 5nov26.xlsx`. It is read-only and **not** copied into the repo; tests use synthetic fixtures. Analysed 2026-11-16 with openpyxl and the real `refined_import.read_refined`.

- **Sheets:** 13 visible (Leiding, Put, Verbindingsstuk, Infrastructureel kunstwerk, Constructieonderdeel, Waterinrichtingsobject, Beheerzone, Reservoir, Gemaal, Kast, Drainagestelsel, Water, Muur).
- **Not present:** no `_designer` sheet and no spec sheets. There are no merged cells, comments, validation, strikethrough or hidden rows.
- **Layout matches `rotterdam_v3`:**
  - A1 is the title (bold, 18 pt); A2 is `Objecttypes:` in italic.
  - Headings use grey `D9D9D9` and blue `D9E2F3` for (Sem.Rel), filled A–E.
  - `(n)` footnotes go with an `Opmerkingen` column, 70 wide: G, H or I.
- **`read_refined` parses all 13 sheets without warnings**, but has the gaps listed under Importer below.
- **Note:** the "Design profile" is not a tab today. It is the Settings → Design profile radio submenu with two hard-coded profiles (`profiles.py:150-190`, `main_window.py:347-357`); nothing is editable in the UI.

## Refinement pointers (evidence → change)
**Profile content (`profiles.py`, `data/rotterdam_v3_relations.json`, `layout_engine.py`)**
1. **New section `Gekoppelde objecten (Sem.Rel)`** before Actoren. It is a single-column list of related objects, varying per type (Leiding!A32:A35, e.g. "Beginpunt leiding", "Constructieonderdelen, etc."). This needs a new section kind, a relation list, in `FixedSection`/`RelationSection` and in the mockup.
2. **New repeater `Inwinningsinformatie (Sem.Rel)`** after Actoren, with Datum | Attribuut | Wijze van inwinning repeated 3× and then `.....` (Put!A40:C46). It is absent on Beheerzone, Kast, Drainagestelsel, Water and Muur (rule: Q-06d).
3. **Memo gains a third column, `Datum`**, on some sheets (Put!C47, Constructieonderdeel!C53); others keep 2 columns (`profiles.py:170`).
4. **Overige informatie** becomes iAssetID, Beheerobjectomschrijving, conversie-id, identificatie and the optional `themaklasse`. `clusternummer` is removed (Leiding!A55:E55). Remove `beheerobjectomschrijving` from `V3_EXCLUDED` (`profiles.py:111`).
5. **Locatie informatie row 2** adds `Distributiegebied` and `Stroomgebied` as derived fields, with the remark "Via Bevind zich in…" (Leiding!C27:D27, G27) (`profiles.py:156`).
6. **`Borden aan drager`** also applies to Waterinrichtingsobject (Waterinrichtingsobject!A26), in the relations JSON.
7. **Grid width stays at 5 (D5).** The PO's 6–7-field rows (Constructieonderdeel!F10, Waterinrichtingsobject!A8:G8) wrap to the next row. The importer accepts wider rows but warns `Row has N fields; the profile allows 5.`
8. **Per-tab exclusion overrides:** Drainagestelsel!A8 shows `Naam` although `naam` is in `V3_EXCLUDED`. In 0.5.0 this is handled by the user, who adds the field via the Design sheet (plan 07). There is no profile change.
9. **Optional ordering by spec:** all four spec waves have `Klasse` and `Volgorde`, for example Object=0, FysiekObject=1, Geo-object=2, RéëlObject=3, Put=7. The engine sorts alphabetically today (`layout_engine.py:208-216`). See Q-06e.

**"Verify with customer" fields (D4, now in [plan 10](0.5.0-10-verify-marks.md))**

10. **Red font (FF0000):** a block of fields at the end of Object informatie on 10 sheets (e.g. Leiding!A16:E22, Gemaal!A14:B24).
11. **Green fill (92D050):** on `Distributiegebied**`/`Stroomgebied`. It means the same thing, "verify with the customer", and is imported as a verify mark (plan 10). This is unrelated to the MDS tints of plan 05.

**Importer (`refined_import.py`)**

12. **Margin column:** take the `Opmerkingen` column found in the header and treat any text right of the last grid column as a remark, not a field. Bug: Waterinrichtingsobject!H21 is read as a field because `Opmerkingen` is in I.
13. **Section headings:** normalise to the canonical titles and warn. Examples: `Inwinningsinformatie (Sem.Rel` without the closing bracket (Put!A40), and the same title without a suffix (Leiding!A42).
14. **Placeholder rows** (`…, etc.`, `.....`) and single-column relation lists are not real fields (Leiding!A35).
15. **`**` suffix:** link it to the margin remark instead of flagging the field as an open question.
16. **Cell colours on import** (red font, `92D050` fill) become the verify mark; this is implemented in plan 10.

**Spec structure (from the 4 spec files)**

17. **Wave-3b grouping** (categories in `Filter`, constant `Fase`): **ignored for now (D8)**.
18. **Orphan types** with attributes but no `Objecttypen` row (`Isolatiekoppeling`, `Waterplanten`) are reported in the Validation tab rather than silently dropped.

## Requirements summary (PO decision D5: update Rotterdam v3, max 5 fields per row)
1. **`rotterdam_v3` itself is updated**; no new profile is added. It generates Leiding, Put and Waterinrichtingsobject so that the cross-reference against the refined workbook shows **no** differences for pointers 1–6. The only expected differences are rows wrapped at 5 fields and the verify marks (plan 10). The Reviewer checks this locally with the PO file; CI uses synthetic fixtures.
2. Rows never hold more than 5 fields (`grid_columns = 5`, unchanged).
3. Importing the refined workbook gives no field from a margin column (12), canonical section titles with warnings (13), and no placeholder fields (14). Rows wider than 5 import with a warning (7).
4. Orphan types appear as validation warnings (18).

## Risks
- Updating `rotterdam_v3` (D5) changes every new export. Users comparing against old exports see the diffs; note this in CHANGELOG.
- The heuristics may overfit one workbook. Keep each rule small and covered by a test.
- An editable profile (JSON in the UI) is **out of scope** for 0.5.0. Propose it for a later release.
