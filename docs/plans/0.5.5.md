# 0.5.5 Plan: no wave-1 road/sign blocks by default, editable relation blocks

Status: done (PO decisions in the request count as approval; deviations listed in the final report) · Base: 0.5.1 (main)

## PO request (summary)
Wave-1 blocks (Wegvakonderdeel, Borden aan drager, ...) sometimes appear in passports of other waves (sewers, waterways, trees). Analyse the passport-template JSON, propose a way to edit the standard semantic blocks (menu item: pick a relation block and name it), and remove the road/sign defaults from the design profile.

## Root cause (grounded)
- `passport_designer/data/rotterdam_v3_relations.json` holds 6 road/sign sections, loaded into `ROTTERDAM_V3.relations` (`profiles.py`).
- `DesignProfile.relations_for()` matches **by filter name only**; `LayoutEngine.build()` (`layout_engine.py` l.103) adds every match.
- The wave-1 filter names are generic and also exist in other waves: *Constructie, Blok, Markering, Paal, Hek, Muur, Constructieonderdeel, Paalconstructie, Waterinrichtingsobject, Straatmeubilair, Weginrichtingsobject*. A sewer or waterway filter with such a name gets *Wegvakonderdeel* or *Borden aan drager*.
- For merged passports `source_filters` = all member filters, so one colliding member is enough.

## Analysis of the template JSON
- The 7 fields `2_17` ... `2_23` are exactly the relation types in `payload.py` (17 Heeft deel, 18 Is verbonden met, 19 Is beschreven door, 20 Bevat, 21 Heeft begrenzing, 22 Voert uit, 23 Bestaat uit). Prefix `2_` = relation element; 24-27 (Speelt, Heeft betrekking op, Beginpunt, Eindpunt) also exist in `payload.py` but not in this template.
- Each is a top-level row with `children: []`: iAsset stores the *relation type* as the block; the columns we draw are our own children.
- `visibilities` is identical for all 7: templates 5398, 5421, 5456, 5521, 6834, all `value "0"`. **Unverified:** whether 0 means hidden, "no value filter" or inherit; `inherit` is false everywhere. Proposal: do not generate or copy `visibilities` until the PO or iAsset confirms the meaning (open question Q1).
- Today only block *titles* decide the relation type (`payload._relation_type`, default 18 with an "assumed relation" warning), so a user-chosen type removes the guessing.

## Design
1. **Remove defaults (all six road/sign sections):** `rotterdam_v3_relations.json` becomes `{"sections": []}`. Loader stays so a user file can still be loaded. Wave-1 behaviour can be restored via a saved block set (below). Tests that expect these sections are updated.
2. **Relation block editor** ("semantic blocks"):
   - **Edit > Relation blocks...** opens a dialog with the blocks of the current passport; actions *Add*, *Rename*, *Edit columns*, *Delete*, *Move up/down*. Also in the section right-click menu of the sheet preview.
   - *Add*: choose relation type (7 from the template, optional 24-27), block name (default = type name + " (Sem.Rel)"), columns (picked from the field catalog or typed), repeat count and repeater yes/no.
   - Scope per block: this passport only (default) / all passports / selected passports.
   - Stored like layout overrides (persisted per passport in the layout store, undo/redo via the existing stack); *Save/Load relation blocks...* as a JSON file in the existing `rotterdam_v3_relations.json` format (+ `element`), so wave-1 can be re-imported.
   - Payload uses the chosen relation type id (`2_<id>`), no assumed-relation warning for user blocks.
   - Name rule: reuse rename validation (non-empty, <= 50, unique within the passport).
3. **Safety net:** a user block is attached by passport (not by filter name), so name collisions cannot leak blocks across waves.

## Decisions (PO)
- Q2: delete the six road/sign blocks completely (no optional file). Instead, make it easy to **rename the standard blocks** (header and optionally example data) to fit the wave being edited.
- Consequence: the editor also covers the standard semantic blocks that stay in the profile (*Gekoppelde objecten*, *Actoren en rollen*, *Inwinningsinformatie*, *Memo*): per passport (or all passports) change the block title, column labels and sample values. Renaming keeps the relation type, so the payload id is unchanged. A *Reset to standard* action restores the default.
- Sample data per block: new optional sample text per column cell (shown in the mockup and Excel).

- Q3: remove *wegcategorie duurzaam veilig* from Beleidsinformatie (also from the fixed names, so it falls back to Object informatie if present in the data).
- Q1 (visibilities meaning) stays open: not emitted until confirmed.

## Steps
1. Empty the default relations file; update tests/docs mentioning the six sections.
2. Model: user relation blocks in `TabOverride` (or sibling store), `LayoutEngine._relation` / `apply_override` insert them; payload maps type to element id.
3. UI: `ui/relation_block_dialog.py`, Edit-menu action(s), context menu, NL/EN i18n.
4. Save/Load block set JSON; migration note for 0.5.x layouts (none needed: old layouts have no blocks).
5. Docs: CHANGELOG 0.5.5, README.md + README.nl.md (menu, wave-1 restore steps).

## Tests
- Default profile builds no road/sign block for any filter name (incl. *Constructie*, *Paal*).
- Add/rename/delete/reorder block; undo/redo; persists in layout store; merged passport keeps blocks.
- Payload: chosen type id used; no assumed-relation warning; name validation.
- Save/Load round trip; UI smoke EN + NL.

## Risks
- Users of 0.5.1 lose the automatic wave-1 blocks: mitigate with a bundled, optional `wave1_relations.json` loadable via *Load relation blocks...* (see Q2).
- `visibilities` semantics unknown: not emitted (see Q1).
- `Beleidsinformatie` still has the optional road field *wegcategorie duurzaam veilig*; only appears if present in the data (see Q3).

## Open questions
- Q1: What does `value "0"` in `visibilities` mean, and should generated relation fields carry template visibilities?
- Q2: Ship the old six blocks as an optional loadable file?
- Q3: Also remove *wegcategorie duurzaam veilig* from Beleidsinformatie?
